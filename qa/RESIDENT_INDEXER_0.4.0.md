# Hyperfinder 0.4.0 상주 인덱서 검증

검증일: 2026-11-09, 로컬 Windows PC.

## 변경

- 검색창과 독립적으로 자동 시작하는 사용자별 Windows 서비스를 추가했다. 검색창은 일반 권한으로 저장 목록을 열고 서비스가 만든 변경분을 받는다.
- NTFS 변경저널을 제한된 크기로 이어 읽는다. 대량 변경이라는 이유만으로 MFT 전체 수집으로 전환하던 한도를 제거했다.
- 일반 파일 변경은 누적 변경 목록으로 전달하고, 검색 데이터는 불변 기준 목록과 바뀐 행을 공유한다. 폴더 구조 변경과 정리 시점에는 메모리 메타데이터로 기준 목록을 다시 만든다.
- 서비스가 시작 중이거나 중지되어 있어도 등록되어 있으면 기존 목록을 먼저 보여주며, 검색창 시작 때문에 기존 전체 폴더 복구나 관리자 보조 프로그램을 실행하지 않는다.
- 완료된 기준 목록과 USN 처리 위치만 공개하며, 파일 작업 후에는 처리 요청 번호를 확인하여 오래된 서비스 결과가 로컬 변경을 덮지 않게 했다.
- 실행파일과 상태 파일은 보호된 Program Files 폴더에 두었다. 서비스 자체 저장 폴더와 사용자 캐시 폴더는 자체 갱신을 유발하지 않도록 제외한다.

## 자동 검사

`cargo check --locked --all-targets`, `cargo fmt --all -- --check`, `git diff --check` 통과.

전체 최적화 검사: 라이브러리 96개, 통합 검사 6개 통과. 광범위한 링크에 걸리는 시간을 줄이기 위해 **검사용 프로필에서만 LTO를 끄고 codegen-units=16**으로 실행했다. 배포 실행파일은 기본 release 설정인 thin LTO/codegen-units=1로 별도 빌드했다.

전체 검사 후 추가한 서비스 정지/기동 중 캐시 우선 처리 변경은 최종 코드의 `resident_updates` 통합 검사와 전체 타깃 컴파일로 재확인했다. 저장 목록 밖에 실제 파일을 만들어도 시작 시 탐색하지 않는지, 숨긴 창이 변경 목록을 받아 새 파일명을 표시하는지, 동일 기준 캐시를 다시 쓰지 않는지 검사한다.

빌드와 동시에 실행한 이전 검사에서 기존 창 응답 시간 제한 검사 1개가 한 번 실패했다. 단독 재검사와 빌드 종료 후 전체 재검사에서는 모두 통과했으며 시간 제한을 완화하지 않았다.

## 실제 NTFS와 설치 서비스

- 관리자 권한 `resident_ntfs_live`: 임시 폴더에 5,000개 파일 생성, 부모 폴더 이름 변경, 삭제, 인덱서 종료 중 파일 생성과 저장 지점 재개를 검증했다. 최초 수집 약 17.95초, 검사 전체 약 32.15초. **최초 수집 이후 추가 전체 스캔 0회**.
- 실제 Windows 서비스 등록과 자동 시작 설정을 확인했다. 최초 저장 목록은 **3,461,532개**, 전체 수집은 **1회**였다.
- 서비스를 실제로 중지/재시작하여 PID가 바뀐 것을 확인했다. 전체 수집 기록은 **1회 그대로**, 상태 오류 없음이었다.
- 일반 권한 `resident_service_live`: 설치된 서비스에 임시 파일 생성/이름 변경/삭제를 요청하고 실제 공개 목록과 변경 목록에서 결과를 확인했다. 생성 반영 약 15.9초, 세 동작 검사 약 21.2초. 전체 수집 횟수는 증가하지 않았다. 이 수치는 요청 직후 검사한 단일 로컬 사례이며 일반 사용의 지연 분포는 아니다.
- 설치 폴더 ACL: SYSTEM/Administrators 쓰기 가능, 해당 사용자 ReadAndExecute, 상속 차단을 확인했다.

원본 로그와 바이너리 해시, 기존 실행파일·설정 백업은 `_workspace/2026-11-09-resident/`에 보존했다. 개인 PC의 파일 목록·설정은 버전 관리에 추가하지 않는다.

## 적용 상태와 검증 범위

상주 서비스와 `dist/Hyperfinder.exe` 모두 0.4.0으로 적용했다. 사용자가 진행 중인 파일 작업이 없다고 확인한 뒤 교체했으며, 실제 교체 시점에는 구버전 프로세스가 이미 종료되어 있어 강제 종료는 필요하지 않았다. 기존 실행파일·설정은 백업되어 있다. 배포 ZIP과 로컬 매니페스트도 갱신했다.

실제 사용자 세션에서 새 GUI의 버전, 서비스 연결, 검색 목록과 새 설정 버튼을 화면으로 확인했다. 새 GUI는 정상 종료됐고, GUI가 종료된 동안 생성한 임시 파일이 서비스의 공개 목록에 포함된 것을 확인한 후 앱을 다시 열었다. 재실행한 GUI에서 그 파일이 검색 결과 1개로 표시됐으며 전체 수집 횟수는 전후 1회로 같았다. 확인용 파일은 정리하고 검색 입력란을 원래 검색어로 복원했다. 마지막 화면 확인은 사용자의 Esc 입력으로 중단됐으므로 검색어·최대화 상태의 최종 저장 확인은 완료하지 않았다. 이 과정에서 관리자 보조 프로그램이나 추가 전체 스캔을 시작하지 않았다. 증거는 `_workspace/2026-11-09-resident/gui-verification.json`에 있다.

이 문서는 로컬 구현 검증 기록이다. PC 재부팅, 물리적 Explorer 드래그, 네트워크/비 NTFS 드라이브는 검증 범위에 포함하지 않았다.
